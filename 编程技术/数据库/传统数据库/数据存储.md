## 传统数据库存储
### 第一步：理解二维表的物理存储

在深入B+树之前，我们必须知道表数据本身是如何存储的。

1. **页/块**：数据库不会一行一行地读写磁盘。它将数据分成固定大小的**页**（例如4KB或8KB）。页是磁盘和内存之间传输数据的基本单位。
    
2. **堆文件结构**：最简单的情况下，所有数据页像一个“堆”一样无序地排列在一起。新行会被插入到有空间的任何页中。
    
3. **行存储**：在一个数据页内，每一行数据（称为**记录**）被紧密地存储在一起。每行除了有我们定义的列（如ID，Name），还会有一些**元信息**，如`NULL`位图、事务ID等。
    

**如果没有索引**，要找到 `WHERE id = 100` 这行记录，数据库必须进行**全表扫描**，即逐个加载所有数据页，并逐行检查`id`字段。这在数据量大时性能极差。

### 第二步：B+树的结构——索引的蓝图

B+树是一种多路搜索树，它就像一本书的**超级目录**。它的特点如下：

- **平衡**：所有叶子节点都在同一层，这意味着查找任何一条记录都需要经过相同数量的节点，性能稳定。
    
- **多路**：一个节点可以有多个子节点（通常是上百个），这使得树非常“矮胖”，极大地减少了查找时需要访问的节点数。
    
- **叶子节点存储所有数据**：这是与B树的关键区别。在B+树中：
    
    - **内部节点** 只存储**键值**（例如`id`）和指向子节点的**指针**。它们是纯粹的导航工具。
        
    - **叶子节点** 存储了所有的**键值**以及与之关联的**数据**。
        
        - **在聚集索引中**：叶子节点存储的就是**整个数据行**。
            
        - **在非聚集索引中**：叶子节点存储的是**索引键值 + 主键值**（或指向数据行的指针）。
            
- **叶子节点双向链表**：所有叶子节点通过指针相互连接，形成了一个有序的双向链表。这对于**范围查询**至关重要。
### 第三步：转换过程——构建索引
#### 1. 排序与页分裂

数据库会（在内存或临时磁盘空间中）将表数据（或索引键）按照 `id` 进行排序。然后开始构建B+树：

- **填充叶子节点**：数据库从最小的 `id` 开始，将 `(id, 整行数据)` 对填入第一个叶子页。当第一个页填满后，创建第二个叶子页，并继续填入。同时，用双向指针连接这两个页。
    
- **构建内部节点**：
    
    - 当有多个叶子页时，需要创建一个**根节点**来指向它们。
        
    - 根节点会提取每个叶子页的**最小键值**（或第一个键值）以及该叶子页的指针。例如，如果第一个叶子页包含 `[5, 10, 15]`，第二个包含 `[20, 25, 30]`，那么根节点可能存储 `[15, ptr1]` 和 `[20, ptr2]`？等等，这里有个常见的误解。
        

**更准确的构建过程是：**  
内部节点存储的是**子节点中键值的范围信息**。通常，它会存储子节点的**第一个键值**（或能起到分割作用的关键值）和指针。一个典型的根节点可能看起来像这样：

`[指针P1, 键值10, 指针P2, 键值20, 指针P3]`  
这表示：

- 所有 `id < 10` 的记录，去P1指向的子节点找。
    
- 所有 `10 <= id < 20` 的记录，去P2指向的子节点找。
    
- 所有 `id >= 20` 的记录，去P3指向的子节点找。
    

随着数据不断插入，节点会分裂，树会向上生长，保持平衡。
### 第四步：B+树如何工作——查询与维护

#### A. 等值查询 `SELECT * FROM Users WHERE id = 25;`

1. **从根开始**：加载根节点到内存。
    
2. **内部导航**：在根节点中，`25 > 15`，所以沿着第二个指针（指向包含更大值的子树）向下查找。
    
3. **到达叶子**：加载下一个内部节点（如果存在）或直接加载叶子节点。在叶子节点中，使用二分查找快速定位 `id = 25` 的记录。
    
4. **返回数据**：因为叶子节点就存储了整行数据，直接返回 `(25, ‘...’, ...)`。
    

**整个过程只发生了 2-3 次磁盘I/O**（树的深度次），而不是成千上万次。

#### B. 范围查询 `SELECT * FROM Users WHERE id BETWEEN 10 AND 25;`

1. **等值查找起点**：先用等值查询的方法找到 `id = 10` 所在的叶子节点。
    
2. **顺序扫描**：由于叶子节点是双向链表，数据库只需从这个节点开始，沿着指针向后顺序读取，直到 `id > 25`。
    
3. **返回数据**：返回所有符合条件的行。
    

**这个过程避免了从根节点重新开始查找`id=25`，效率极高。**

#### C. 插入 `INSERT INTO Users VALUES (18, ...);`

1. 定位到 `18` 应该被插入的叶子页。
    
2. 如果该页有空间，直接插入并保持有序。
    
3. 如果该页已满，则进行**页分裂**：
    
    - 将原页的数据大致平均分成两半。
        
    - 创建一个新的叶子页。
        
    - 将后半部分数据移到新页。
        
    - 在父节点（内部节点）中添加一个新的键值和指针，指向新页。
        
    - 如果父节点也满了，分裂会向上传递，可能导致树长高。
## 非索引查询
当查询条件无法使用索引时（如您说的，只有`id`有索引，却要按`age`查询），数据库会退而求其次，使用最基础但保证准确的方法。

这个过程就是 **全表扫描**。

### 核心机制：全表扫描

既然`age`列没有索引，B+树无法提供快速定位，数据库只能“老老实实”地检查表中的每一行，看看它是否满足 `age > 10` 的条件。

**具体步骤：**

1. **定位起点**：数据库通过表的元数据，找到属于这个表的**第一个数据页**。
    
2. **加载页**：将这个数据页从磁盘加载到内存的**缓冲池**中。
    
3. **逐行扫描**：
    
    - 数据库会遍历这个数据页内的**每一行**记录。
        
    - 对于每一行，它读取`age`列的值。
        
    - 应用 `age > 10` 这个条件进行判断。如果为真，则将这行记录加入到结果集中。
        
4. **获取下一页**：当前页的所有行都检查完毕后，数据库通过数据页之间的**页链表指针**，找到下一个数据页的ID。
    
5. **循环**：重复步骤2-4，加载下一个页，继续扫描，直到处理完表的**最后一个数据页**。
    

---

### 全表扫描的性能挑战与优化

全表扫描听起来很慢，确实，对于大表来说，它是性能杀手。但数据库引擎并不会“傻乎乎”地执行，它内置了多种优化策略：

#### 1. 缓冲池：减少磁盘I/O

- 数据库有一个重要的内存区域叫**缓冲池**。
    
- 当数据库读取一个页时，会将其缓存在缓冲池中。
    
- 如果后续的查询（甚至是其他查询）再次需要这个页，它可以直接从内存中读取，避免了昂贵的磁盘I/O。
    
- 在全表扫描期间，缓冲池就像一个“滑动窗口”，不断换入新的数据页。
    

#### 2. 顺序预读

这是针对全表扫描最重要的优化。

- **机制**：当数据库检测到正在进行顺序扫描（例如，正在按页链表顺序读取页）时，它会启动一个**预读**线程。
    
- **工作方式**：这个线程会**异步地**提前将接下来可能要访问的多个数据页加载到缓冲池中。
    
- **效果**：当主查询线程处理完当前页，准备处理下一页时，下一页很可能已经被预读线程加载到内存中了。这极大地减少了查询线程的等待时间，将大量的随机I/O转换成了更高效的批量顺序I/O。
    

#### 3. 并行表扫描

在一些高级的数据库系统（如PostgreSQL, Oracle）中，对于非常大的表，查询优化器可能会决定启动**多个工作进程**来并行扫描一张表。

- 每个进程负责扫描表的一个不同部分。
    
- 最后将所有进程的结果合并起来。
    
- 这充分利用了多核CPU的能力，可以显著缩短扫描时间。

### 执行计划可视化

如果您使用数据库管理工具（如MySQL的`EXPLAIN`, PostgreSQL的`EXPLAIN ANALYZE`），执行 `SELECT * FROM users WHERE age > 10;`，您可能会看到这样的执行计划：

**在MySQL中：**

sql

EXPLAIN SELECT * FROM users WHERE age > 10;

输出可能包含：

text

type: ALL
key: NULL
rows: 1000000
Extra: Using where

- `type: ALL`：这就是在明确告诉你，它将进行**全表扫描**。
    
- `key: NULL`：表示没有索引可用于此查询。
    
- `Using where`：表示它将在存储引擎层逐行应用 `WHERE age > 10` 条件。
## 多条件查询
如果一次查询有多个查询条件，会触发多棵B+树吗？有些是有索引的，有些是没有索引的？只要有个条件是没有索引的，那么是否无可避免的就要全表扫描了？

### 核心策略：索引选择与“最左前缀”原则

优化器首先会查看所有可用的索引，并评估使用哪个索引的成本最低。即使只有一个条件能用上索引，它也可能选择使用那个索引，而不是直接全表扫描。

#### 场景1：多个条件，其中一个有索引

假设我们有一个 `Users` 表，在 `age` 列上有索引 `idx_age`，但 `name` 列上没有索引。

**查询：** `SELECT * FROM Users WHERE age > 25 AND name = 'Bob';`

- **优化器的可能策略：**
    
    1. **使用 `idx_age` 索引**：
        
        - 数据库首先通过 `idx_age` 索引树快速找到所有 `age > 25` 的记录的**主键ID**。
            
        - 然后，对这些主键ID进行**回表**操作，从主键索引树中取出每一行的完整数据。
            
        - **最后，在内存中对这些取出的行应用 `name = 'Bob'` 这个条件进行过滤。**
            
    
    - **为什么这么做？** 如果 `age > 25` 能过滤掉表中90%的数据，那么数据库只需要回表检查剩下的10%的数据。这比全表扫描（检查100%的数据）要高效得多。
        

**在这种情况下，触发了 `idx_age` 这棵B+树，并没有直接进行全表扫描。**

#### 场景2：多个条件，其中有联合索引

这是更常见且更高效的情况。假设我们在 `(country, city)` 上创建了一个联合索引。

**查询A：** `SELECT * FROM Users WHERE country = 'China';`

- **效果：完美使用索引。** 因为联合索引的第一个字段是 `country`。
    

**查询B：** `SELECT * FROM Users WHERE country = 'China' AND city = 'Beijing';`

- **效果：完美使用索引。** 同时用上了索引的两个字段。
    

**查询C：** `SELECT * FROM Users WHERE city = 'Beijing';`

- **效果：无法使用这个联合索引！** 因为跳过了左边的 `country` 字段。这就像电话簿按（姓，名）排序，你无法只用“名”来快速查找。
    
- **结果**：在这种情况下，如果 `city` 列没有单独的索引，优化器**很可能**会选择全表扫描。
    

---

### 高级策略：索引合并

在一些更先进的数据库（如MySQL）中，优化器还有一种叫做 **索引合并** 的武器。

假设 `Users` 表有两个独立的索引：`idx_age (age)` 和 `idx_name (name)`。

**查询：** `SELECT * FROM Users WHERE age > 25 OR name = 'Bob';`

- **单个索引的困境**：
    
    - 没有哪个索引能单独解决这个 `OR` 条件。
        
- **索引合并的工作流程**：
    
    1. **同时触发两棵B+树**：数据库的执行引擎会**并行地**执行两个索引扫描：
        
        - 通过 `idx_age` 索引查找所有 `age > 25` 的主键ID集合。
            
        - 通过 `idx_name` 索引查找所有 `name = 'Bob'` 的主键ID集合。
            
    2. **合并结果**：对这两个主键ID集合执行**并集** 操作（因为是 `OR`）。
        
    3. **回表**：根据合并后的主键ID集合，去主键索引中进行回表，获取完整数据。
        
- **对于 `AND` 条件**：如果查询是 `WHERE age > 25 AND name = 'Bob'`，索引合并则会对两个ID集合取**交集**，然后再回表。
    

**索引合并的本质是：通过同时查询多棵B+树，在“主键ID”这个层面上进行集合运算，从而缩小需要回表检查的数据范围。**

---

### 总结：优化器的决策过程

当面对一个多条件查询时，优化器会像一个精明的侦探一样权衡：

1. **全表扫描的成本**：需要读取所有数据页。成本与表大小成正比。
    
2. **使用单个最佳索引的成本**：
    
    - 通过索引找到的主键ID数量（基数估算）。
        
    - 回表的成本（每次回表都是一次B+树查找）。
        
    - 在内存中过滤无索引列条件的成本。
        
3. **索引合并的成本**：
    
    - 扫描多个索引的成本。
        
    - 合并大量ID集合的成本。
        
    - 回表的成本。
        

**最终，优化器会选择它认为成本最低的那个执行计划。**

### 结论与最佳实践

|情况|优化器可能采取的策略|是否全表扫描|
|---|---|---|
|**所有条件都无索引**|无计可施，只能**全表扫描**。|**是**|
|**只有一个条件有索引**|**使用该索引**，回表后过滤其他条件。|**否**|
|**有联合索引，但查询条件不满足最左前缀**|可能放弃使用该索引，转而全表扫描或使用其他索引。|**很可能**|
|**多个条件有独立索引（OR）**|可能使用**索引合并**。|**否**|
|**结果集非常大**|优化器可能认为使用索引+大量回表的成本**高于**直接全表扫描，从而选择全表扫描。|**是**|
